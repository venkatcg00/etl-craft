# CLAUDE.md — etl-craft

## What this is

`etl-craft` is a standalone, metadata-driven ETL orchestration engine. It is barebones by design, ships as a PyPI package (uv-compatible), and is meant to be adoptable by any team, independent of which orchestrator — if any — they use. This repo is **Repo 1** of a two-repo split: the engine itself, with zero domain knowledge and no team-specific pipelines baked in. A separate `metadata-etl-implementation` repo (not this one) will hold a reference implementation ("Support Insights") that proves the engine works at scale, and evolves independently of the engine.

The whole pipeline/task/step/dependency structure is modeled as **rows in Postgres**, not as Python DAG files or model files. The engine reads that metadata and executes it; it never writes logic it wasn't explicitly given.

## Where things stand / where to start

**Iteration 1 is feature-complete; the iteration-2 backlog is `ITERATION_2.md` — read it before starting new work (2026-09-20).** Every scope item this file describes is built (24 modules, 368 tests passing, CI green). A full code review of the finished result is written up in `ITERATION_2.md` as a numbered, prioritized backlog (`E2-01`…`E2-40`), with four P0 correctness bugs each **reproduced against real Docker Postgres** during the review — a `FAILURE`-gated task making a successful pipeline report `FAILED`, a duplicate invocation clobbering a still-running task's log row, engine-created tables that can never pass `validate`'s own primary-key check, and SCD merges permanently breaking on duplicate `MERGE_KEY` source rows. It also records the packaging finding that the built wheel ships no `sql/` at all (so there's no way to create the schema, and `etl-craft migrate` silently no-ops), plus a "deliberately not on this list" section so settled decisions don't get re-litigated. Anything in that file marked "from code" needs a confirming test written first; several items name a design question to raise rather than guess at.

**Iteration-2 scope set (2026-09-20).** A planning session walked the backlog against the live code, confirmed every claim it spot-checked, and set scope to **all 40 items** — plus three genuinely new ones that came out of the design decisions made there, recorded in `ITERATION_2.md`'s own "Added during iteration-2 planning" section along with the phase order and the decisions that are now settled: **E2-41** conditional dependency cardinality (`CFG_TASKS.RUN_CONDITION` = `ALL`/`ANY`/`N`, resolved into Airflow trigger rules at DAG-generation time), **E2-42** every SQL action except `DROP_TABLE`/`DELETE_ROWS` creating its target if absent, and **E2-43** a redesigned pipeline-level, three-flavour (`SUCCESS`/`COMPLETED_WITH_ERRORS`/`FAILED`) `EMAIL_ALERT` that supersedes the task-level design described under "Handlers" below. **Iteration 2, phase 1 — dependency semantics and run status — done (2026-09-20).** Closes `ITERATION_2.md`'s E2-01, E2-02, E2-37 and E2-41, plus the `trigger_rule` half of E2-14. Four interlocking pieces, landed as one change because each is load-bearing for the others:
- **E2-41, conditional dependency cardinality.** **[ADDITION, post-signoff schema change]** `CFG_TASKS` gains `RUN_CONDITION` (`ALL`/`ANY`/`N`, NULL means `ALL`) and `RUN_CONDITION_COUNT`, with two `CHECK` constraints — per explicit instruction that a task depending on 10 others should be able to run once at least one meets its condition. `resolver.DependencyGraph.required_edge_count()` is the new pure primitive; `ready()`'s old `all(...)` over edges became a count comparison against it, so every pre-E2-41 row (NULL → ALL) behaves exactly as before. **[CHOICE]** the columns live on `CFG_TASKS`, per explicit instruction ("these should be resolved while dag chain generation itself") — a per-task mode maps 1:1 onto an Airflow trigger rule, which an OR-group on `CFG_TASK_DEPENDENCY` could never do. **[CHOICE]** named `RUN_CONDITION` rather than the also-offered `RUN_TYPE`, since `CFG_PIPELINES.REFRESH_TYPE` already owns the `*_TYPE` shape here. `build_graph` validates the mode standalone (so the resolver stays usable without a live Engine DB) *and* rejects a count larger than the task's own edge count — genuinely beyond what any `CHECK` can express, since it spans two tables, so `validate` surfaces it through `validate_graphs`.
- **E2-01, a `FAILURE`-gated task making a successful pipeline report `FAILED`.** New `resolver.DependencyGraph.unsatisfiable()` — the counterpart to `ready()`, returning never-run tasks whose edges can never be satisfied — plus `orchestrator.settle_unsatisfiable_tasks()`, which records them `SKIPPED`. Called from *both* the wave loop (every pass, since one `SKIPPED` can unblock a downstream `ALWAYS` edge) and `_finalize_from_task_states`, so `--finalize-only` under `Mode=orchestrator` — the generated DAG's `__finalize__` step, and that mode's only finalize path — is correct too. **The load-bearing detail**: an edge is permanently unsatisfiable only when its upstream is in the *new* `resolver.SETTLED_STATUSES` (`SUCCESS`/`SKIPPED`), deliberately **not** `TERMINAL_STATUSES` — `FAILED` stays retry-eligible per "retry resumes", and converting a merely-failed upstream into a downstream skip would report a broken run as `SUCCESS`, which is worse than the bug. A dedicated test pins that boundary. `orchestrator.py` now imports `SETTLED_STATUSES` from `resolver.py` rather than keeping its own identical copy (E2-35's spirit, applied while the file was open).
- **E2-02, a duplicate invocation clobbering a still-running task's log row.** `runner.run_task()` gains an explicit `IN-PROGRESS` branch beside the existing `SUCCESS` short-circuit, placed *before* the dependency check: it writes **nothing** and exits 0. `resolver.ready()` excludes an `IN-PROGRESS` task deliberately ("never re-dispatch"), and the dependency check could only read that exclusion as "dependencies not met" — so a second invocation used to overwrite the live row with `SKIPPED`, which lied in the audit log, disarmed the original process's crash detection (it only writes `FAILED` while the row still reads `IN-PROGRESS`), and left the outcome depending on which process wrote last. Reachable by ordinary means: an Airflow retry firing mid-run, or a human running a task the local orchestrator already spawned. The blanket skip reason also became honest — `_describe_unready()` now distinguishes "not yet" from "never will be", and both name how many of how many edges are needed.
- **E2-14's `trigger_rule` half.** **[DEVIATION]** `generate-yml`'s `depends_on` entries now carry `trigger_rule` instead of the raw `dependency_type` — one vocabulary, not two side by side, per explicit instruction ("dont do two parameter types"). `generate_yml.trigger_rule_for()` maps `(RUN_CONDITION, DEPENDENCY_TYPE)` onto `all_success`/`one_success`/`all_failed`/`one_failed`/`all_done`/`one_done`. Two combinations genuinely have no Airflow equivalent and are stated in the module docstring rather than papered over: `RUN_CONDITION='N'` (Airflow has `all_*`/`one_*` and nothing in between) and `HAS_DATA` (Airflow cannot see `TARGET_COUNT`). Both emit the permissive rule and leave the real gate to the engine, which fails safe — Airflow starts the task, the engine then records it `SKIPPED` if the condition isn't met.
- **E2-37** fixed in passing while `resolver.py` was open: `_check_acyclic` uses an explicit stack, so a chain deeper than Python's recursion limit raises `ResolverError`, not `RecursionError`.
- **First real migration file.** `sql/migrations/0001_add_run_condition.sql` — the mechanism built for open question #7 had never actually applied anything outside a test's `tmp_path`. Writing it immediately surfaced E2-05's documented `;`-splitting limitation *for real*: an earlier draft mentioned the semicolon character inside its own header comment and broke on itself. Two consequences, both kept: the file is written with no semicolon anywhere except as a statement terminator, and it drops each constraint before adding it (Postgres has no `ADD CONSTRAINT IF NOT EXISTS`, and this runner has no `$$` block available), so it is genuinely re-runnable as `sql/migrations/README.md` requires. The pre-existing `test_cli_migrate_reports_up_to_date_with_no_pending_files` was rewritten into `..._applies_the_real_migrations_directory_and_is_idempotent`, which now runs `migrate` twice against real Postgres — the only test that exercises a genuinely shipped migration rather than a synthetic one.
- **27 new tests (368 → 395), 99.8% coverage, `make check` and `make db-schema-test` both clean.** The E2-01 and E2-02 tests were each verified to *fail* against the pre-fix code before being kept, not merely to pass after it — the review's own rule for turning a reproduction into a regression test. `sql/schema_test.sql` gains 3 `EXPECT SUCCEED` and 4 `EXPECT FAIL` cases for the new constraints (12 `EXPECT FAIL` total, up from 8), each verified to land exactly on its marked statement. Manually verified end-to-end through the real CLI against Docker Postgres: `generate-yml` emitting `one_success` for an `ANY` task with three upstreams; that task passing its gate with only one upstream succeeded; and a `FAILURE`-gated `EMAIL_ALERT` on a successful pipeline finalizing `SUCCESS` (exit 0) with an honest `SKIPPED` row naming why — the exact scenario that reported `FAILED` before.
  - **Behaviour worth knowing, not changed here**: a task recorded `SKIPPED` is settled, so a manual `run --task_code` that gates it off early makes it un-runnable for the rest of that pipeline run even if the dependency is satisfied later. That follows from "retry resumes... skips what's already `SUCCESS` or `SKIPPED`" and predates this work; noted because the smoke test above walked straight into it.

**Iteration 2, phase 1b — the round-2 review's own findings — done (2026-09-20).** Phase 1 was independently re-reviewed and nine follow-on findings (`E2-44`…`E2-52` in `ITERATION_2.md`) were raised against it, six reproduced. All nine are fixed. The pattern worth remembering: **most of them were in the new surface phase 1 created, not in what it fixed** — E2-41 was specified over "a task's dependencies" but implemented over `same_pipeline_edges` only, because `fetch_pipeline_graph` deliberately filters cross-pipeline edges out before `build_graph` ever sees them.
- **E2-44/E2-45, resolved by explicit decision: `RUN_CONDITION` ranges over ALL of a task's edges, cross-pipeline included.** A task author writing "depends on 10 tasks, any one will do" has no reason to care which pipeline an upstream lives in. `TaskNode` gained `cross_pipeline_edge_count` (the edges themselves still stay out of the graph — the resolver has no way to settle them — but the *count* has to reach the arithmetic), `cfg.fetch_pipeline_graph` populates it, and **[DEVIATION]** `crosspipe.check_task_cross_pipeline_dependencies` now returns a `CrossPipelineCheck` (satisfied count, total, per-edge reasons) instead of the first-failure `str | None`, which could only ever express ALL. `runner.run_task` counts both halves against one requirement rather than gating them one after the other. Before this, `ANY` silently meant "any same-pipeline edge **and** every cross-pipeline edge", and `N` rejected a valid cross-pipeline config outright with "it could never run". **Real upside the new shape buys:** `check_task_cross_pipeline_dependencies` takes a `needed` count and stops once it is reached, so an `ANY` task whose condition is already met from the same-pipeline side never polls a cross-pipeline edge at all — previously it could block a process (and an orchestrator worker slot) for up to an hour on an edge it did not need.
  - **[CHOICE], and the non-obvious part:** `ready()` treats *unevaluated* cross-pipeline edges optimistically — as though satisfied — and uses real counts only when a caller supplies them. That is not laziness: `ready()` is also `orchestrator._run_until_settled`'s wave pre-filter, and the real cross-pipeline gate runs *inside* the spawned `run --task_code` subprocess. Counting them pessimistically there would deadlock — the task would never be spawned, so the check that settles it would never run. `unsatisfiable()` counts them as still-possible for the same reason: this module cannot see `AUD_*_DEPENDENCY_TRACKER`, so it must never doom a task on the strength of the half it can see.
- **E2-46, resolved by explicit decision: `trigger_rule` moved from the edge to the task.** Airflow's `trigger_rule` is a property of the *task* — one value, applied to all its upstreams — but phase 1 emitted it per `depends_on` edge, which is only coherent while every edge of a task shares one `DEPENDENCY_TYPE`, and nothing requires that. A task with a `SUCCESS` edge and an `ALWAYS` edge emitted two conflicting rules, handing a loader a choice it cannot make correctly — precisely the failure that emitting `trigger_rule` instead of the raw type was meant to prevent. `depends_on` is now a plain list of task names, and `generate_yml.task_trigger_rule()` resolves one rule per task; mixed types give the permissive `all_done` and let the engine gate, the same documented fail-safe already used for `N` and `HAS_DATA`. Preserves every currently-valid config rather than forbidding mixed types.
- **E2-47: "not yet" and "never" are no longer recorded the same way.** `SKIPPED` is terminal (`NOT_RETRYABLE`, `SETTLED_STATUSES`), so writing it for a task whose dependency simply hasn't run *yet* permanently disqualified that task from the run — a later invocation, even with the upstream genuinely `SUCCESS`, still refused, and the pipeline finalized `SUCCESS` with the task never having run. CLAUDE.md explicitly supports the paths that hit this ("a manual single-task run, a backfill, a re-triggered task"), so the verification must not be destructive. **[DEVIATION]** only the permanently-unsatisfiable case writes a terminal row now; "not yet" writes **nothing** and exits 0, the shape E2-02 established for `IN-PROGRESS`. A cross-pipeline edge that came back unsatisfied still writes `SKIPPED` — `crosspipe` just polled it to its budget, so it has had its chance, which is what "correctly gated off by design" means.
- **E2-48, resolved by explicit decision: both halves.** The generated `__init__` edge emits `all_success`, not `all_done` — with `all_done`, a failed run-minting step still started every root task, and each took `resolve_run_for_task`'s dev/ad-hoc fallback into the *previous, already-finalized* run and rewrote its rows. And `resolve_run_for_task` now refuses to bind to an already-**finished** run without `--force`. **[CHOICE]** `FINISHED_RUN_STATUSES` is `SUCCESS`/`FAILED` only, deliberately **not** `SKIPPED`: a `SKIPPED` run is what `orchestrator.py` writes when a pipeline's own cross-pipeline gate was never met, precisely so every task binding to it records `SKIPPED` in turn. Binding there is additive and intended; binding to a `SUCCESS` or `FAILED` run overwrites rows already reported on. That distinction was caught by an existing test failing, not by review — the first version of the guard broke the cross-pipeline gating flow outright.
- **E2-49 + E2-39 (pulled forward from phase 7, same line of defence): `main()` has no path left that tracebacks on a non-bug.** `ResolverError` joins `RUN_ERRORS` (E2-41 gave `build_graph` four new ways to raise, and `--finalize-only` now builds a graph where it previously did not, so a config problem could take out a generated DAG's synthetic *last* step), `_graph_command` builds its graph inside its own `try`, and a top-level `SQLAlchemyError` catch covers every command — `list` and `generate-docs` previously had none at all, so an unreachable Postgres printed a raw traceback.
- **E2-50: `settle_unsatisfiable_tasks` could re-create E2-02's clobber from the other side.** It read `run_state` in one transaction and wrote in another, with nothing re-checking that the rows were still absent — so a concurrent `run --task_code` that created the row and started executing in between got overwritten with `SKIPPED`. The window is real, not theoretical: it runs on every wave pass while subprocesses are live. `TaskRunBinding` gained `created: bool`, and settle now writes one transaction per task, only when *it* created the row.
- **E2-51/E2-52, both made deliberate rather than silent.** `waves()` stays the guaranteed-safe static order and deliberately ignores `RUN_CONDITION` (**[CHOICE]** — "earliest possible" and "guaranteed safe" are different questions, and its two consumers, `graph` and `run_pipeline(force=True)`, both want the second); `graph` now names any task whose `RUN_CONDITION` lets it start earlier. And every generated YAML file carries a header explaining why `tasks:` speaks `trigger_rule` while the informational `pipeline_dependencies`/`cross_pipeline_task_dependencies` blocks keep the raw `dependency_type` — they describe `CFG_` rows, not anything Airflow executes, so there is no task for a rule to attach to.
- **407 tests (up from 395), 99.8% coverage, `make check` and `make db-schema-test` clean.** **Method note worth keeping:** the E2-50 regression test initially passed for the *wrong* reason, and coverage is what exposed it — seeding the `IN-PROGRESS` row up front means `unsatisfiable()` excludes the task before the `created` guard is ever reached, so the guard line stayed uncovered while the test went green. It now drives the interleaving explicitly (monkeypatching `fetch_run_state` to create the row after returning state) and was verified to fail without the guard. A regression test for a race has to actually reach the race.
- Manually verified end-to-end through the real CLI against Docker Postgres: the new one-rule-per-task YAML shape (roots on `all_success`, a mixed-edge task on `all_done`, `__finalize__` on `all_done`, plus the explanatory header), and `run --task_code` refusing cleanly (exit 1, one line) against a pipeline whose latest run is already `SUCCESS`.

**Iteration 2, phase 2 — SQL action correctness — done (2026-09-20).** Closes `E2-03`, `E2-04`, `E2-42`, `E2-31`, `E2-33` and E2-25's crash half. One pass over `sql_actions.py`'s action bodies; no schema change (every addition is a `CFG_TASK_PARAMETERS` convention, per this project's established practice).
- **E2-03, `PRIMARY_KEY`.** CLAUDE.md states "every target table is required to have a single-column primary key — an enforced framework convention", checked by `validate` through introspection — but every table this module creates is built with `CREATE TABLE ... AS SELECT`, which never creates one, so the engine's own tables could never satisfy the engine's own convention. New optional `CFG_TASK_PARAMETERS.PRIMARY_KEY`, applied as `ALTER TABLE ... ADD PRIMARY KEY` after the CTAS by every creating action, and **re-applied by `_evolve_schema` after its drop-and-rename**, which would otherwise destroy it. **[CHOICE]** deliberately independent of `MERGE_KEY`, per explicit instruction ("a merge can have both primary key and merge key") — a target's identity and the columns a merge matches on are different questions even when they coincide. **Known, now-stated limit of the same mechanism**: the evolution rebuild does *not* recreate indexes or grants, only the primary key this module knows about.
- **E2-42, create-if-absent.** Per explicit instruction ("apart from drop and delete, everything should create a table if the target does not exist, using select query and adding audit columns"), `_check_or_evolve_schema` now bootstraps a missing target (`_create_target_shape`: the staged SELECT's business columns, plus `PIPELINE_RUN_ID` and that action's own `AUDIT_COLUMNS`, plus the declared primary key, created empty with `WHERE 1 = 0`) instead of raising "run a SETUP_TABLE or CREATE_TABLE task against it first". `DROP_TABLE`/`DELETE_ROWS` unchanged. A first run of `OVERWRITE_TABLE` or either SCD merge no longer needs a separate setup task.
- **E2-04, `MERGE_DEDUPE_ORDER`.** Nothing checked that the staged SELECT yields one row per `MERGE_KEY`, and the target had no primary key to catch it either — so two source rows sharing a key silently corrupted an SCD1 target on run 1 (both took the `NOT EXISTS` insert leg, leaving two "current" rows, reported `SUCCESS`), then killed it permanently on run 2 with a cardinality violation from the correlated `SET col = (SELECT ...)`. By then the duplicates were in the *target*, so no retry could recover it without manual SQL. `_dedupe_stage` now runs **before any statement touches the target**. **[CHOICE], per explicit decision:** duplicates are resolved by a declared ordering (`MERGE_DEDUPE_ORDER`, an `ORDER BY` fragment) and **rejected outright when none is declared** — the engine will not invent an ordering nobody gave it, since which row survived would be undefined and could differ between runs. The dedupe itself is `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` into a new temp table rather than a `DELETE`, because deleting duplicates in place needs a dialect-specific row identity (`ctid`, `ROWID`) — the one thing this module works hardest to avoid.
- **E2-25's crash half, `split_object_ref()`.** A `TARGET_OBJECT` with no dot raised a bare `ValueError: not enough values to unpack` from inside the crash-detection fork, so the parent reported only its generic "died unexpectedly" fallback — a traceback-shaped message about a config typo. Worse, `qualify()` didn't validate either (it just prefixed the database), so the creating actions silently emitted a *malformed two-part name*. One validating splitter now backs `qualify()` and all three former `split(".", 1)` sites.
- **E2-31/E2-33, portability — and a real ClickHouse finding the tests surfaced.** `_hash_expression` uses ANSI `CAST(... AS VARCHAR)` instead of Postgres's `::text` shorthand; `_add_hash_key`'s `UPDATE` lost its non-ANSI target alias; `AUDIT_COLUMN_TYPES` gained lengths on `VARCHAR` (bare `VARCHAR` is rejected in DDL by several dialects) and `TIMESTAMP WITH TIME ZONE` for `CREATE_DATE`/`UPDATE_DATE` (schema.sql uses `TIMESTAMPTZ` throughout and the engine writes `datetime.now(UTC)`, so every warehouse-side audit timestamp was silently losing its offset). The module docstring now states plainly that the atomicity guarantee is **DDL-dependent** and does not hold on MySQL/Oracle, rather than leaving it implied.
  - **Two ClickHouse differences, both verified against the live container rather than assumed** — the "prove it for real" bar `warehouse.py`'s own ClickHouse test set. (1) ClickHouse's `MD5()` returns `FixedString(16)` — raw bytes — where Postgres's returns 32 hex characters, so `HASH_KEY VARCHAR(32)` stored the wrong thing entirely there; the dialect branch wraps it in `lower(hex(...))`. (2) **Found only because the test ran against real ClickHouse, not from reading code**: `CAST(col AS VARCHAR)` raises `CANNOT_INSERT_NULL_IN_ORDINARY_COLUMN` on a nullable column the moment any value is NULL, and the surrounding `COALESCE` *cannot* rescue it because the cast is evaluated first. The branch casts to `Nullable(String)` there instead. Both keyed off `conn.dialect.name`, never an import — the pattern `cloning.py` already established. `_apply_primary_key` is likewise a no-op on ClickHouse, where ordering is a table-engine property fixed at `CREATE` time and there is no `ALTER TABLE ... ADD PRIMARY KEY` at all.
- **416 tests (up from 407), 100% coverage on `sql_actions.py`, `make check` clean.** The E2-04 test was verified to fail against the pre-fix code — without the guard, run 1 reports `SUCCESS` while writing both duplicate rows, which is exactly the silent corruption. One pre-existing test (`..._missing_target_fails_clearly`) asserted the behaviour E2-42 deliberately reverses and became `..._creates_a_missing_target`.

**Iteration 2, phase 3 — `EMAIL_ALERT` redesigned as a pipeline-level completion alert — done (2026-09-20).** Closes `E2-43`. Designed by interview during iteration-2 planning rather than guessed at; supersedes the task-level design the original module was built around. No schema change — every addition is a `CFG_TASK_PARAMETERS` convention.
- **Scope moved from the task to the run.** Per explicit decision ("task level emails are noise"), one email per pipeline run. `email_alert.run_flavour()` computes it from every active task's status under this `pipeline_run_id` via `cfg.fetch_task_statuses_for_run`, **not** from `AUD_PIPELINES_RUN_LOG` — under `Mode=orchestrator` the run isn't finalized until the `__finalize__` step, which is after the alert.
- **Three flavours**, worst-first: `FAILED` (any task FAILED) → `COMPLETED_WITH_ERRORS` (nothing failed outright but something short of clean — a `SKIPPED` task, a task carrying an `ERROR_MESSAGE` while succeeding, or a task not settled yet) → `SUCCESS` (every task SUCCESS, none carrying an error). The middle one is the literal case the instruction named: "if the pipeline is marked success with failure then a neutral status like pipeline is COMPLETED with errors". **[CHOICE]** unsettled tasks (`PENDING`/`IN-PROGRESS`) land in the neutral middle rather than `SUCCESS` — the alert is *designed* to run at the end but nothing forces it to, and reporting a plain `SUCCESS` for a run that hasn't finished is the one genuinely misleading answer of the three.
- **The alerting task excludes itself**, which needed `cfg.TaskStatusEntry` to carry `task_id` (it previously exposed only `task_code`). An `EMAIL_ALERT` task is necessarily `IN-PROGRESS` while it runs, so counting it would make every single run resolve to `COMPLETED_WITH_ERRORS`. Easy to miss, and it would have made the feature useless rather than merely wrong.
- **Three templates, one chosen** ("have three templates as said in flavour answer and choose 1 as needed"): optional `EMAIL_SUBJECT_<STATUS>`/`EMAIL_BODY_<STATUS>`, each falling back to the plain `EMAIL_SUBJECT`/`EMAIL_BODY`. That fallback is why every pre-existing `EMAIL_ALERT` test kept passing untouched — a task declaring only the plain pair behaves exactly as before. New `$$status` substitution token, and a coloured flavour banner above the existing intro/digest.
- **`EMAIL_ON_STATUS`**, pipe-separated ("if there are parameters saying which status to send, send only on that condition, else send on all statuses"). When the computed flavour isn't in the list the task records **`SUCCESS`** with `EMAIL_SENT = false` and the reason in `TASK_LOG` — deliberately not `SKIPPED`: it ran and correctly decided not to act, and `SUCCESS` keeps it out of the unsettled set so it can never re-create E2-01. An unrecognized value is a clean `HandlerError`, not a silent no-send.
- **426 tests (up from 416), 100% coverage on `email_alert.py`, `make check` clean.**
- **Still open, deliberately**: `COMPLETED_WITH_ERRORS` currently keys off a `SKIPPED` task or a non-null `ERROR_MESSAGE` on a succeeded row, because today's schema cannot distinguish "succeeded first time" from "succeeded on retry" — `update_task_run` overwrites in place. E2-21's `ATTEMPT_COUNT` (phase 7) is what makes that computable; worth revisiting the definition once it lands, as `ITERATION_2.md` records.

**Iteration 2, phase 4 — the install path — done (2026-09-20).** Closes `E2-13`, `E2-05`, `E2-06`, `E2-15`, `E2-16`. `CLAUDE.md`'s first paragraph says the engine "ships as a PyPI package (uv-compatible), and is meant to be adoptable by any team" — a team running `uv add etl-craft` could not previously reach a working Engine DB by any route.
- **E2-13, the wheel shipped 24 `.py` files and nothing else.** No `sql/`, no `py.typed`, no license, and `[project]` had no `license`/`classifiers`/`keywords`/`urls`. `sql/` therefore **moved to `src/etl_craft/sql/`** — uv_build packages `src/<module>/` only — with `[tool.uv.build-backend] source-include` shipping it and `py.typed`. New `packaged_sql.py` reads it through `importlib.resources` rather than `__file__` arithmetic, so it behaves the same from a checkout, a wheel, or a zipimport. `docker-compose.yml`, the `Makefile` and CI all point at the new path (verified by a full `docker compose down -v` + re-up, so the schema genuinely re-applies from there).
- **New `etl-craft init-db`** (`init_db.py`), the verb that was missing entirely: applies the packaged schema to an empty database. **Refuses** a database that already has engine tables — `schema.sql` is plain `CREATE TABLE` and deliberately not idempotent, so re-running it would fail half-applied; the refusal names what it found and points at `migrate`. `--force` overrides, and is never used on the engine's own initiative.
- **E2-05, `migrate` silently no-opped.** Its `Path(__file__).parents[2]` default resolved above `site-packages` once installed, and `Path.glob` on a nonexistent directory yields nothing *without error*, so it printed "already up to date" and skipped a team's migrations. Resolution is now `--migrations-dir` → `$ETL_CRAFT_MIGRATIONS_DIR` → `./sql/migrations` → the packaged copy, and a directory that doesn't exist is a clean error rather than silence. `SCHEMA_MIGRATIONS` is created if absent (a database predating it previously produced an uncaught `ProgrammingError`), and a Postgres advisory lock spans the whole run so two concurrent `migrate` calls can't double-apply.
  - **The `;`-splitting limitation is fixed, not just documented.** `split_statements` is now a small scanner tracking single-quoted strings (with their `''` escape), dollar-quoted bodies including tagged `$tag$` ones, and `--`/`/* */` comments. It had to be: `schema.sql`'s own trigger functions are `CREATE FUNCTION ... $$ ... ; ... $$` bodies, so `init-db` could not have worked at all under the old `split(";")`, and the review's prediction that this would be "very likely the *first* migration anyone writes" was if anything understated.

## Core design principles

These aren't stylistic preferences — violating them undoes decisions made deliberately over a long design conversation:

- **Config vs. code, drawn by blast radius, not convenience.** A step that only reads/writes within the platform (a `CFG_` row) is config — low-friction, eventually CLI-driven. A new external connection, a new action type, or a destructive schema change is code — reviewed, deliberately harder to change. Creating a new pipeline is *always* manual (git-managed inserts/migrations), never a CLI verb.
- **Closed vocabulary of SQL actions.** `CREATE_TABLE`, `SETUP_TABLE`, `OVERWRITE_TABLE`, `SCD1_MERGE`, `SCD2_MERGE`, `DROP_TABLE`, `DELETE_ROWS` — implemented in `sql_actions.py` (see "Where things stand"), the authoritative reference for the exact vocabulary and mechanics now that it's built. Every SQL-handler task supplies a bare, validated, read-only `SELECT`; the engine wraps it in whatever statement the declared action calls for, and appends whichever engine-managed audit columns that action calls for — never present in the author's own SELECT. The engine owns every write — a step cannot touch the warehouse outside its declared action. Cover new needs by extending an existing action's metadata, not by adding a new action type casually.
- **Order comes from data.** `CFG_TASK_DEPENDENCY` / `CFG_PIPELINE_DEPENDENCY` rows are the DAG. Nothing enumerates order in code; the resolver just walks dependency rows. Same-pipeline order compiles into Airflow's native task chaining when generating YAML; cross-pipeline order has no structural equivalent in any orchestrator and is always resolved by self-check/polling at runtime.
- **Idempotent by construction, retry resumes.** Re-running a step must produce the same result whether it runs once or five times. A retry reads the log, skips what's already `SUCCESS` or `SKIPPED`, and only re-attempts what actually failed or never ran.
- **One run id, resolved, never passed.** `pipeline_run_id` is never handed between tasks — no XCom, no injected env var. Every task independently resolves the currently-active run by querying `AUD_PIPELINES_RUN_LOG`. See "Run-id resolution" below; this is probably the single most load-bearing mechanism in the whole design.
- **Full-refresh/derived state by default; incremental only where provably safe.** A table either accumulates every run (history) or holds exactly one run's truth (current state) — never a mix.

## Non-goals — things explicitly considered and rejected

Do not reintroduce these without a real reason; each was deliberately ruled out during design:

- REST API calls to any orchestrator, including Airflow, at execution time. The only hard runtime dependency, checked by every action, is a valid Engine DB (Postgres) connection.
- XCom, or any other orchestrator-specific mechanism, for passing `pipeline_run_id` between tasks.
- Importing `dag-factory` or any other orchestrator-specific library. `generate-yml` is entirely hand-rolled — the YAML shape takes visual inspiration from how Airflow/dag-factory-style YAML looks, for familiarity, but is not required to match any external tool's schema, and no such library is a dependency.
- Support for more than one Data DB (warehouse) connection per deployment. One warehouse, full stop — the explicit reasoning given for this was "else we will become Informatica."
- Any runtime detection scheme for whether execution mode is being spoofed (credential-probing, install-time locks were both considered and dropped). Final stance: trust the developer. `--mode` is never a runtime flag typed by a human for orchestrator runs — it's baked in once, at setup time, via `set-execution-mode`, and persists in `craft-connector.yml` until the environment is rebuilt.
- Sourcing credentials from an orchestrator's own connection store (e.g. reading Airflow Connections directly). All connections resolve through `craft-connector.yml` only, to stay orchestrator-agnostic — this includes the Data DB connection, "even on the Airflow side."
- ~~A SQL parser dependency.~~ **Reversed 2026-09-20 by explicit instruction** ("sql parser to implement column level lineage. dont re-invent the wheel use metadata and any existing package that can do this"). `sqlglot` is now a hard dependency, used only by `column_lineage.py`. Writing our own was considered and rejected on the instruction's own terms ("if it is easy implement our own, else go with hard dependency") — it is not easy, and a hand-rolled parser would be subtly wrong in exactly the cases lineage is consulted for. Note `validate`'s read-only lint (E2-07) deliberately stays a string check: it is a lint, not a parse, and does not need one.
- Bundling third-party SQLAlchemy dialects (Snowflake, Databricks, BigQuery, Redshift, ClickHouse) as hard dependencies. They're optional extras a team installs itself; SQLAlchemy discovers an installed dialect automatically via setuptools entry points, so engine code never imports one directly.
- A heartbeat column plus an external "reaper" process for detecting dead tasks. Superseded by parent/child process monitoring — see "Crash detection" below.
- A staging/cross-connection copy path for ordinary tasks. Moot by construction once there's only one Data DB — `source_object`/`target_object` are always in the same place.

## Architecture at a glance

**Two databases, two very different rule sets:**
- **Engine DB** — always Postgres, no exceptions. Holds every `CFG_`/`AUD_` table. Required specifically for Postgres's constraint guarantees — most importantly, a partial unique index is what makes run-id creation race-safe (see below). Every engine action checks for a valid Engine DB connection first, before anything else.
- **Data DB / warehouse** — exactly one per deployment, any SQLAlchemy-supported relational engine. Because there's only one, `TARGET_OBJECT`/`SOURCE_SQL` in `CFG_TASK_PARAMETERS` always resolve against that same database — there is no cross-connection staging path to build for ordinary tasks. `TARGET_OBJECT` is stored as bare `schema.table`, deliberately environment-agnostic — the database/catalog name is always supplied at runtime from the active `[Warehouse]` profile (`sql_actions.qualify()`), so the same CFG_ row means a different real object in dev/uat/prod.

**Connections & auth** — all resolved through `craft-connector.yml` (below), never hardcoded, never sourced from an orchestrator. JDBC URL is the preferred storage format for a connection string wherever one is persisted; a small internal translator converts it to the right SQLAlchemy dialect URL at connection time. Auth is a small registry of functions keyed by each profile's `auth_mode` (`password`, `token`, `sso`, `key_file`), handed to `create_engine(creator=...)` — the `sso`/`token` modes mint or refresh short-lived credentials per connection. For those two specifically, `pool_recycle` should sit comfortably under the credential's real lifetime so a checked-out connection always has meaningful life left — that's a safety margin, not a guarantee; a connection dying mid-operation is just another failure the idempotent-retry design already absorbs. `pool_pre_ping` is a worthwhile optimization on top but not load-bearing.

**Execution — one primitive.** Everything runs through `etl-craft run --pipeline_code X [--task_code Y] [--force]`:
- `--task_code` given → runs exactly one task. This is the literal form Airflow's generated `BashOperator` tasks shell out to.
- `--task_code` omitted → runs the whole pipeline. The engine becomes its own tiny scheduler: resolve the ready wave from `CFG_TASK_DEPENDENCY` (the same resolver `graph` uses to walk the same data, just consumed differently), spawn one `run --task_code` subprocess per ready task, wait on the wave, repeat. Local runs are built to mimic exactly what an orchestrator-driven run does — sequential/parallel waves, subprocess-per-task, crash monitoring — unless `--force` is passed.
- `--force` bypasses all dependency/state checks entirely, for a pipeline or a single task. Only legal under `Mode = local`; refused outright under `Mode = orchestrator`.
- There is deliberately no separate `execute --local`/`execute --airflow` verb, and no REST-based trigger/status command — `run` is the only execution primitive, in both modes.

**Execution mode (`local` vs. `orchestrator`)** is set once per environment via `etl-craft set-execution-mode`, persisted in `craft-connector.yml`. It is **not** a per-invocation CLI flag — nothing in a generated DAG or a manual command line passes `--mode`. Changing it means re-running setup, which in a real deployment goes through the same versioned pipeline as any other environment change. This is intentionally a trust boundary, not a technical one: see the Non-goals entry above.

**Crash detection.** `run` forks the actual task logic as a child process and watches it. A child that exits normally — success, or a handled failure — writes its own final log row, as always. A child that dies unannounced (OOM-kill, segfault) gets `FAILED` written on its behalf by the still-alive parent. This is identical in local and Airflow modes, since Airflow-side execution is this same subprocess form — nothing orchestrator-specific to build. Known, accepted gap: if the *entire* process tree dies at once (container OOM-killed, pod evicted, node gone), nothing survives to write `FAILED`. Airflow's own zombie-task detection covers its UI in that scenario but never touches `AUD_TASK_RUN_LOG`, which is left permanently stale. Accepted as rare enough not to solve for now.

## Run-id resolution (read this before touching anything related to run state)

`pipeline_run_id` is never passed to a task — every task resolves it itself by querying `AUD_PIPELINES_RUN_LOG`:

1. The first task of a run does a **find-or-create**: reuse an existing `IN-PROGRESS` row for this pipeline if one exists; otherwise mint a new one.
2. This must be atomic at the database level — a trigger or application-level check alone cannot close the race between two near-simultaneous kickoffs of the same pipeline. The actual guarantee comes from a **partial unique index**: `UNIQUE (PIPELINE_ID) WHERE STATUS = 'IN-PROGRESS'`. The second concurrent insert fails outright rather than racing. This is implemented in `sql/schema.sql` as `ux_pipeline_run_one_active`.
3. Every later task queries for whatever run is currently active for its pipeline and binds itself to it (one `AUD_TASK_RUN_LOG` row per task per pipeline run, found-or-created and updated in place — never a new row per retry attempt).
4. If a task already has a binding under that run and it already shows `SUCCESS`, it returns success immediately without re-running. This is what makes retries — whether triggered locally or by an orchestrator — always *continue* a failed/in-progress run rather than starting fresh, and is why a run should never end in an intermediate state.
5. A single-task invocation with nothing currently active is a dev/ad-hoc convenience path: it binds to the latest logged run and updates its dates. Not an everyday scenario — don't over-engineer around it.

## Incremental / full-refresh mechanics

- `CFG_PIPELINES.REFRESH_TYPE` (`FULL`/`INCREMENTAL`) is a **pipeline-level** value — every task in one pipeline run shares one mode. Mixing an always-full dimension load with an incremental fact load means two pipelines, not one. **Note:** both pasted schema drafts still show `REFRESH_TYPE` on `CFG_TASKS` — that was superseded by a later, explicit decision to move it to the pipeline. `sql/schema.sql` implements the pipeline-level version; `CFG_TASKS` carries a comment noting the column is intentionally absent there.
- Every SQL step's `SELECT` may contain the literal token `$$pipeline_id` in its `WHERE` clause. The engine runs its own plain-text substitution pass *before* the query reaches the driver's own bind-variable handling, so `$$` tokens and real bind params (`:param`, `%s`) never collide.
- At substitution time: `$$pipeline_id` becomes `pipeline_run_id = <this run's id>` for incremental, or `1=1` for full refresh.
- **Refined 2026-09-20, per explicit instruction, to two further cases** (`sql_actions.substitute_pipeline_id`): if the token is absent and the `SELECT` has **no `WHERE` clause at all**, the engine appends one itself, so an author doesn't have to remember the token on every ordinary query; if the token is absent but a **real `WHERE` clause already exists**, the query is left completely untouched — "you may need to enforce it on static tables as well, which is wrong," since a small reference/lookup table with its own filter and no `PIPELINE_RUN_ID` column must never get one silently `AND`-ed on. The "has a `WHERE`" check is a plain regex, not a real parse — a `WHERE` that exists only inside a subquery would be mis-detected as present at the top level; a known, flagged heuristic limit, not solved further.
- **[SUPERSEDED, same day, 2026-09-20]** The auto-append bullet directly above was reverted per explicit correction ("this was a bad idea"). `substitute_pipeline_id` is back to a strict two-case rule: token present → substitute; token absent → leave `sql` **completely untouched**, `WHERE` clause or not — no heuristic `WHERE`-detection, no auto-append. A missing token on a genuinely incremental source is now treated as a reviewable pipeline-definition mistake, not something the engine tries to silently rescue. See "Where things stand"'s own dated entry for the full reasoning and the new audit-column-presence check added alongside it.
- Every table written by a SQL action carries a `pipeline_run_id` column that the engine auto-stamps. A step author writes `select col1, col2 from table where $$pipeline_id` — never manually selects or inserts the id.
- **`HANDLER = PYTHON` ingestion scripts are the one exception.** The engine does not auto-inject the run id into them; the team's own script is responsible for fetching and including `pipeline_run_id` in whatever it inserts.
- Runtime substitution, rather than trusting a stored value, matters specifically for full refresh: it's what lets a downstream table that maintains history, with no new data after change-detection, still correctly carry the *current* run's id instead of getting stuck showing some run from long ago.
- `HAS_DATA` (`TARGET_COUNT > 0`) is only a meaningful signal against an **incremental** upstream — there it genuinely reflects whether anything changed, and downstream tasks can legitimately skip on it. Against a full-refresh upstream, every run re-asserts the complete current state regardless of whether values actually moved, so `HAS_DATA` isn't a real change signal there — full refresh just proceeds and re-stamps.

## Dependency resolution & polling

- **Same-pipeline task deps**, when going through a generated DAG, compile into Airflow's own native task chaining (`>>`), built from `CFG_TASK_DEPENDENCY` — series, parallel, conditional shapes, as the data dictates.
- **Any path that bypasses the DAG's own ordering** — a manual single-task run, a backfill, a re-triggered task — has no structural ordering to lean on, so the engine still has to verify same-pipeline dependencies itself: a live query against `AUD_TASK_RUN_LOG` scoped by the shared `pipeline_run_id` (no staleness comparison needed, since both tasks already share one run).
- **Cross-pipeline dependencies** (`CFG_PIPELINE_DEPENDENCY`, and `CFG_TASK_DEPENDENCY` rows where `DEPENDS_ON_PIPELINE_ID` points elsewhere) have no DAG-native equivalent in Airflow or otherwise — one DAG can't natively depend on a task in a separate DAG. These are always resolved by a self-check/poll step inserted before step 1, alongside run-id minting.
- The naive version of this check — "look at the dependency's last logged run" — breaks the moment two pipelines run on different schedules (weekly vs. daily, say): most days the dependency isn't in-progress, so the check falls straight to a stale "last logged run" from days ago and wrongly proceeds. The fix: two watermark tables, `AUD_PIPELINE_DEPENDENCY_TRACKER` and `AUD_TASK_DEPENDENCY_TRACKER` (in `sql/schema.sql`, not in either pasted schema draft — designed later), recording the run last *consumed* for each dependency edge. A candidate run only satisfies the edge if it's newer than what was already consumed for that specific edge *and* matches that edge's own `DEPENDENCY_TYPE` — a `SUCCESS` edge tracks the last `SUCCESS` run, `FAILURE` tracks the last `FAILED` run, `HAS_DATA` tracks the last run with `TARGET_COUNT > 0`. Until a new qualifying run appears, the edge keeps resolving to "not yet satisfied," with no polling wasted on a pipeline that was never going to produce one today.
- The tracker only updates *after* the gated task/pipeline completes. Cross-pipeline task-level tracking only applies to actual cross-pipeline edges — same-pipeline task deps never touch it.
- Poll only while the dependency is genuinely `IN-PROGRESS`; if it isn't, go straight to the tracker comparison above rather than polling blindly.
- Poll cadence, as specified: a hard 1-hour timeout overall. The interval strategy is duration-aware rather than fixed — based on the dependency's average run duration and current elapsed time, first poll at 70% of that average, next at 80%, +10% each poll after, capped at 30 polls total. Whichever limit is hit first (poll count or the 1-hour wall clock) ends the wait. **Resolved (2026-09-19, open question #4): the percentage-based schedule alone governs.** The earlier "exponential backoff of 60 minutes" mention is stray/superseded, not a second real mechanism — confirmed directly, not guessed at. When no duration history exists yet for a new pipeline pairing (nothing to compute 70%/80%/etc. of), there's still no separate backoff fallback specified; see this build's own `[CHOICE]` on what fills that gap.

## Business rules

- `CFG_BUSINESS_RULES.BUSINESS_RULE_TYPE` (`INCOMPLETE`/`REJECT`) classifies the **row** a rule flags — it is not a pass/fail outcome. Rule *run* outcome (did the check itself execute successfully) is tracked separately, in `AUD_BUSINESS_RULES_RUN_LOG.STATUS`.
- Ordering is `SEQUENCE_NUMBER` (dense rank per task) directly on `CFG_BUSINESS_RULES` — same rank runs in parallel, different ranks run sequentially. There is no separate business-rule dependency table.
- Every target table is required to have a single-column primary key — an enforced framework convention, which is why `BUSINESS_RULE_KEY_COLUMN` can safely stay a single column rather than a list. This convention lives outside the Engine DB entirely (it constrains tables in the Data DB), so it cannot be checked by an Engine DB constraint — enforce it at `validate` time via schema introspection against the Data DB.
- A flagged row's classification is audit information, not a failure signal — a business-rule task that flags every row it checks is still a `SUCCESS` task run. Nothing here auto-blocks a pipeline; that would have to come from a separate, explicitly-declared task dependency on the BR task's own status.

## Handlers

Four, closed: `PYTHON` (ingestion scripts, `scripts.py`), `SQL` (engine-executed, wraps a bare `SELECT` per the closed action vocabulary, `sql_actions.py`), `BUSINESS_RULES` (drives `CFG_BUSINESS_RULES` rows for that task, `business_rules.py`), `EMAIL_ALERT` (added later than the other three — not in either pasted schema draft, but confirmed; SMTP send, `email_alert.py`, done 2026-09-20 — see "Where things stand" for the full design, including its HTML/CSS status-digest mode). An `EMAIL_ALERT` task is gated the same way any other task is, via a normal `CFG_TASK_DEPENDENCY`/`CFG_PIPELINE_DEPENDENCY` row — a `FAILURE` edge fires only when what it watches fails, `ALWAYS` fires regardless. No separate conditional mechanism needed.

**`EMAIL_ALERT` redesigned (2026-09-20, iteration 2 phase 3, `E2-43`) — it is now a pipeline-level completion alert, not a task-level one.** Per explicit interview decision: "task level emails are noise", and "once you exhaust retries and all of the tasks that can be run are ran and failed, then send one email considering all". One email per run, whose **flavour** — `SUCCESS` (green) / `COMPLETED_WITH_ERRORS` (amber) / `FAILED` (red) — is computed by `email_alert.run_flavour()` from every active task's own status under this `pipeline_run_id`, read from `AUD_TASK_RUN_LOG` rather than `AUD_PIPELINES_RUN_LOG` (which may not be finalized yet when the alert runs). Optional per-flavour `EMAIL_SUBJECT_<STATUS>`/`EMAIL_BODY_<STATUS>` templates each fall back to the plain `EMAIL_SUBJECT`/`EMAIL_BODY`, and optional `EMAIL_ON_STATUS` restricts which flavours actually send. The gating sentence above still holds — this changes what the task *does* once dispatched, not how it is dispatched.

## craft-connector.yml

Versioned, no secrets stored directly in it — analogous to a dbt `profiles.yml`. Structure so far:

```yaml
[Execution]
Mode: local | orchestrator       # set via `set-execution-mode` at setup time only, persists until rebuild
Orchestrator name: <optional>    # informational only, engine doesn't act on it

[Source]
Type: file | environment         # where actual secret values live
Path: <path>                     # required when Type = file (a .env-style file)

[Postgres]                       # Engine DB — required, always Postgres
Active_profile: <name>
Profiles:
  dev:  { host, port, user, auth_mode, ... }
  sit:  { ... }
  uat:  { ... }
  prod: { ... }

[Warehouse]                      # Data DB — optional (see "Data DB / warehouse connector layer" above); resolved open question #1
Active_profile: <name>
Profiles:
  dev:  { host, port, user, auth_mode, ... }
  sit:  { ... }
  uat:  { ... }
  prod: { ... }

[Cloning]
Enabled: true | false            # opt-in, off by default — nothing is copied unless explicitly turned on
Scope: cfg | aud | all           # which table groups mirror into the Data DB, merge-style

[Orchestrator]                   # optional — global defaults/fallbacks for generate-yml's Airflow-facing fields
Global_dag: true | false         # emit the optional cross-pipeline trigger DAG — defaults to false
Catchup: true | false
Tags: [tag1, tag2]
Retries: <int>
Retry_delay_minutes: <int>
Depends_on_past: true | false
Email_on_failure: true | false
Email_recipients: [addr1, addr2]

[Email]                          # optional — required only if any active task uses HANDLER=EMAIL_ALERT; added 2026-09-20
Active_profile: <name>
Profiles:
  dev:  { host, port, from_address, auth_mode, user, use_tls, ... }
  sit:  { ... }
  uat:  { ... }
  prod: { ... }
```

`auth_mode` per profile selects one of a small registry of connection-creator functions (`password`, `token`, `sso`, `key_file`) — see Architecture above. `[Email]` profiles use their own, smaller `auth_mode` vocabulary (`none`, `password`) — see `email_alert.py`'s own module docstring for why `token`/`sso` aren't included there.

**Cloning**, specifically: a merge-style copy of selected Engine DB tables into the Data DB, so a team can query engine config/audit from inside their own warehouse without a separate Postgres connection. Runs after each pipeline run, only when enabled. This is special-cased engine-internal machinery — it does not reopen the "one Data DB, no general cross-connection support" rule that applies to ordinary tasks. **Done (2026-09-20)** — `src/etl_craft/cloning.py`; see "Where things stand" for the full mechanism (truncate-then-reinsert per table, generic cross-dialect column types, a same-database safety refusal, and the real ClickHouse-specific fixes this required).

## Database schema

Full DDL (complete first draft, needs review and sign-off) is at `sql/schema.sql`. It has been applied to a real local Postgres 16 and exercised against `sql/schema_test.sql`, which confirms — by actually triggering them, not just reading the DDL — that every load-bearing mechanism behaves as this file describes: the audit trigger stamps and preserves the right columns, the enum/conditional `CHECK` constraints reject what they should, the `DEPENDS_ON_PIPELINE_ID` default-from-sibling trigger fires, self-dependency is blocked, the partial unique indexes correctly allow a deactivated natural key to be reused while blocking a second active duplicate, and — the one that matters most — the `AUD_PIPELINES_RUN_LOG` partial unique index really does block a second concurrent `IN-PROGRESS` run for the same pipeline while leaving a second pipeline's own `IN-PROGRESS` row and any terminal-status row untouched. Re-run `sql/schema_test.sql` (instructions in its header) after any schema change that touches these mechanisms. Summary of tables:

**Config tables** — `CFG_PIPELINES`, `CFG_PIPELINE_DEPENDENCY`, `CFG_TASKS`, `CFG_TASK_DEPENDENCY`, `CFG_TASK_PARAMETERS`, `CFG_BUSINESS_RULES`.
**Audit tables** — `AUD_PIPELINES_RUN_LOG`, `AUD_TASK_RUN_LOG`, `AUD_BUSINESS_RULES_RUN_LOG`, `AUD_BUSINESS_RULES_RESULTS`, `AUD_TASK_OFFSET_TRACKER`, `AUD_PIPELINE_DEPENDENCY_TRACKER`, `AUD_TASK_DEPENDENCY_TRACKER`.
**Migration bookkeeping** — `SCHEMA_MIGRATIONS` (added 2026-09-20, see "Where things stand" and `sql/migrations/README.md`) — not a `CFG_`/`AUD_` table, purely for `etl-craft migrate`'s own use.

All primary keys use `GENERATED ALWAYS AS IDENTITY`. The pasted schema notes annotate almost every validated column as "(WILL BE ENFORCED BY THE ENGINE SETUP AS TRIGGER)" — `schema.sql` does **not** implement all of these as literal trigger functions; see its header and closing summary block for exactly which ones became real triggers (only where a `DEFAULT`/`CHECK` genuinely cannot do the job — namely `CREATED_BY`/`UPDATED_BY` capture, and `CFG_TASK_DEPENDENCY.DEPENDS_ON_PIPELINE_ID`'s default-from-sibling-column) versus which became plain `CHECK` constraints (all the enum-style value lists). This is a real, deliberate divergence from the literal pasted text — flagged prominently for sign-off, not silently decided.
